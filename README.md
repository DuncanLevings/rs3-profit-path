# Profit Path

An RS3 plugin for finding money-making methods suited to your account.

Early development: version 0.7.1-dev contains an independent resizable workbench with a sidebar, searchable browser of four method versions, favourites, dedicated method tabs and the first income calculator. Method rows now separate titles, compact profit figures and actions; sidebar highlights show the selected section and activity. Income has a compact results band and side-by-side input/output tables, with input (cost) values in subtle red and output (earnings) values in subtle green; Requirements groups Skills, Required items, Recommended items, Quests and Other, colouring confirmed text checks green or red. Item lists use native icons with name-only tooltips; missing ROI text is omitted. The full catalogue and recommendations are still in development. It sends no game inputs and stores character bindings, personal method rates, character-specific favourites, a device-wide sort choice and historical counts of catalogue-relevant items.

## Project layout

Runtime Lua, tests and build tools live under `src/`. The root `main.lua` only starts the app and exposes its shutdown hook because the client requires that entry point. `data/` stays at the top level, alongside the manifest, readable JSON sources and notices. Install the runtime files (`main.lua`, Lua modules within `src/`, `data/*.lua`, manifest and notices), excluding `src/tests/` and `src/tools/`. UI code is in `src/ui/`; native account reads and requirement checks in `src/game/`; browsing/calculations in `src/methods/`; preferences in `src/storage/`; the monster reader in `src/data/`.

## Development setup

Use the RS3 plugin beta. Put the project folder in its `dev_plugins` directory as `profit-path`. Install PrettyUI (6398181) and rsprite 0.1.2 in the adjacent `rsprite` development folder. After installing or changing dependency manifests, manually rescan plugins (`prf`), load/reload rsprite (`prl rsprite`), then reload Profit Path (`prl profit-path`). rsprite is not yet on the Plugin Hub; the manifest currently uses its development-folder dependency. GE Prices Library 0.3.1 is a required dependency (it supplies every price): put it in the adjacent `gepl` development folder and enable it through the client. This build does not enable dependencies or grant permissions itself. GEPL owns its HTTP access; its quote getter may refresh its cache.

Enable or reload `profit-path` and open its ribbon panel in the Plugins window. Click **Open Profit Path** to open the separate in-game window; the ribbon page is only a launcher and does not open it automatically. Open **Smelting steel bars** for the first complete calculator. Both elder-log versions and the melee abyssal demon method also have complete income models; unknown live prices still prevent a total estimate. Complete bank coverage, equipment matching and general unlock detection are still unverified.

Use **Browse** or **Favourites**, then an activity category and the search field. Sort by **Profit** or **ROI**, highest or lowest first, and narrow the list with the **Difficulty** and **Intensity** filter dropdowns (filters are not saved). Captions label the sort pair and each filter, with a divider between the groups. Dropdown changes check each entry with `GetEntrySelected(id)` on one deferred Logic callback (the `selectedEntries` collection returns numbers that don't reliably match entry IDs on this client), then unsubscribe; there is no recurring sort polling. Unknown values stay last in either direction, with title/ID ties kept consistent. Difficulty is not yet researched for these samples, so a specific difficulty filter currently matches none of them; a saved Difficulty/Intensity sort from older builds falls back to Profit. Search matches titles, variants and source categories as plain text. Back from a method keeps the list section, category, search, sort and scroll position while the plugin remains enabled.

Opening or reopening Browse captures prices for complete method models; opening/reopening a method refreshes its own quote set without resetting a draft. Search and sorting reuse captured estimates, with no polling or manual refresh button. Back uses captured method quotes with its saved/source rate rather than an unsaved draft. Incomplete models show unavailable estimates. Browse category colours match the sidebar: PvM red, skilling green and production blue, and method titles keep their colour under every activity filter. Each method row is a card with a slightly lighter fill and a thin activity-coloured bar on its left edge.

**Resizing.** PrettyUI views size their inner content when built and expect `SetSize` when space changes. While the window is open and visible, Profit Path reads its content size once per logic tick and compares two numbers; the check stops when the window is hidden or closed. Once a new size has held for 15 ticks (0.3 s at 50 ticks/second) it rebuilds the current screen once. (The native `ONRESIZE` hook did not fire for PrettyUI window resizes in game.) The rebuild keeps the Browse filters and scroll position, the open method tab and the draft rate. The method tabs sit at x = 0, so both sides get PrettyUI's same 14-unit page padding. A page that grows a scrollbar gets narrower, but PrettyUI panels keep the inner width they were built with; so once a screen is built, every Browse row and Income/Requirements panel is resized to its page's final width with the documented `Panel:SetSize` (full width minus padding, or half width for side-by-side panels with an 8-unit gap). Star and arrow icons provide favourite/open actions with tooltips.

Drag and resize the window using its native frame. Navigation replaces only the content view, so moving between methods and Browse keeps the frame's position and size. Closing hides it; reopening retains the current screen, draft rate and tab. A game-state transition destroys the window because its native parent may change; reopen it explicitly afterward. Placement is not persisted across reloads or game-state transitions in this build.

This is a development manifest; release contact metadata and the published GEPL dependency mapping will be added before submission. This build requests no permissions and does not read character tracking IDs; the account context uses only the local visible display name. The identity probe was removed after a reported client crash when granting tracking access; the cause is still unconfirmed.

Quest requirements use verified, non-deprecated quest config names (from Skill Tips' verified config data); The Temple at Senntisten uses `TEMPLE_AT_SENNTISTEN`. Missing, deprecated or failed quest reads remain unknown or explicit errors.

## Requirement checks

`src/game/requirements.lua` evaluates plain account evidence and returns `met`, `unmet` or `unknown`, keeping source wording. It supports base skills, the client's combat level, completed quests, unlock flags (game variables such as relics and ability codices, where any non-zero value is unlocked), achievements and diary tiers, named-item quantities, nested all/any groups and curated equipment alternatives. Access and recommendations are checked separately: a missing recommended item does not block access. Browse has a Requirements dropdown beside Intensity: All, Met, Missing or Needs checking. Cards do not show readiness labels, and the sidebar retains navigation and activity categories. On narrower windows the three filters wrap together beneath sorting. An incomplete source requirement model cannot produce an overall Access met verdict.

`src/main.lua` gathers only the skills, quests and items referenced by this small catalogue. `src/game/account.lua` reads base levels, native quest flags and relevant backpack/worn/bank counts. Inventory events invalidate the affected container; skill events do not read inventories, and inventory events do not read skills or quests. Only progress variables supplied by a mapped quest trigger a quest refresh. The workbench updates while visible; opening it rebuilds the evidence. A game-state transition clears the live evidence, ends its character binding and destroys the window. There is no gameplay polling or tracking-ID access.

Item borders mean green for observed live ownership, red for absence when last checked in all three containers, gold for a historical saved hint and grey for unavailable evidence or an unverified native item ID. A saved bank is **not** added to live counts or used to confirm ownership. Tool-belt hatchets, pickaxes and mattocks are checked through native mappings; other belt categories, Diango and other storage remain unverified. An unreadable container cannot establish a new absence. An earlier explicit zero remains a last-checked red border, clearly identified by the saved-store footer; a never-checked item stays grey. These historical display hints do not change live access verdicts. The Requirements footer identifies each store as live, saved or unavailable.

`src/storage/account_snapshot.lua` owns a separate `profit-path.account.v1/` record per existing character profile. It stores plain, catalogue-relevant counts by container, never native objects or a full arbitrary bank dump. There is no timestamp or age claim: any loaded/unreadable-container evidence is historical regardless of when it was saved. Counts stay in memory during inventory events; dirty records flush on close, container removal, profile/session change or shutdown. The application caps each stored container at 4,096 item IDs (not a client storage-limit claim). Invalid records retain valid containers as hints but are protected from overwrite; write failures show a warning and remain retryable within the binding. Unsaved hints can be lost if a failed write is followed by shutdown or a character change. Rates and favourites use their existing keys.

Equipment alternatives select the highest observed candidate that meets the requirement and its verified use levels. The generic matcher supports minimum tiers, styles and slots; the initial shipped mappings cover hatchets and spring cleaners 2000/3000/5000/9000, **not a complete weapon/armour catalogue**. Native item names must match bundled names before an item can qualify. Partial equipment-variant coverage stays unknown when no match is found. The detail page keeps the original requirement wording and shows an identified owned match as a native item icon with a name-only tooltip. When no match is identified, it shows the reason without an empty item slot. Explicit named minima (such as Spring cleaner 2000+) instead show their minimum icon, with a red border when all qualifying variants were absent at the last check, or grey when never fully checked. An owned upgrade replaces that icon. This is validated source metadata, not an arbitrary example for highest-tier-tool requirements. A saved match is explicitly historical. Abyssal demon item alternatives and the recommended Temple quest are connected, but its overall setup coverage remains partial; no recommendation engine is implemented yet.

`catalogue-source/methods.json` contains verified native variable/enum binding names for three tool-belt families. `src/game/toolbelt.lua` reads each presence/selection variable and calls the client's item enum with its verified offset: hatchet/pickaxe keys are zero-based; the mattock value is one above its key. This resolves every listed native variant rather than hard-coding bronze or copying the item tables. Invalid values, missing enums, wrong enum types and native failures stay unknown. A mattock value producing a negative key is unknown, not assumed absent. The initial displayed items were verified as bronze hatchet, steel pickaxe and bronze mattock against native values 0/5/1.

Tool-belt evidence is plain, live-only data, cached until its varbit or base-variable event changes, and cleared on character/session changes and shutdown. Only requested item IDs feed method ownership. A belt tool establishes one usable tool without adding another tradeable copy to inventory quantities; it is never written into bank/backpack snapshots. Matching source equipment also checks use levels, and shows the item with **On your tool belt**. All 17 normal hatchet entries are mapped in the source; their rank uses Wiki cutting power separately from use/combat levels. This does not implement all tool-belt categories or a complete gear catalogue. No runtime scan, HTTP request, permission or tracking-ID access was added.

The entry point `main.lua` is the required client entry point; it starts `src/main.lua`, which connects account reads, requirements, the calculator, preferences and navigation. `src/game/account.lua` owns inventory/skill/quest/game-state subscriptions and the tool-belt cache; `src/game/toolbelt.lua` resolves native tool-belt selections; `src/ui/workbench.lua` separately owns the launcher, workbench frame and current content view. `src/methods/browser.lua` owns filtering, ordering and list state; `src/ui/browse_view.lua` owns the sidebar, header and scrollable result views. `src/ui/method_view.lua` renders the four detail tabs. `src/methods/income.lua` owns GE quote interpretation and pure arithmetic; `src/storage/preferences.lua` owns user choices and `src/storage/account_snapshot.lua` owns historical item evidence. `src/ui/item_icon.lua` validates native icon lookups; `src/ui/view_style.lua` shares colours and number formatting between Browse and details. Shutdown unsubscribes owned callbacks, invalidates screen/row callbacks, then destroys child views, content, frame and launcher. This build makes no direct network requests.

## Calculator and saved rates

The steel-bar recipe uses the Wiki's base 2,000 smelts/hour model. Inputs use GEPL's instant-buy side, outputs its instant-sell side. The output tax is rounded down per item before multiplying the quantity. The UI labels revenue/profit after tax without listing tax amounts; calculations keep their full precision while money displays round to whole GP. Net profit is revenue after tax minus supply costs; ROI is net profit divided by supply cost. A zero denominator shows not applicable. These trade quotes differ from the Wiki's GE guide prices.

Opening or reopening a method captures its direct-item quote set. The library owns HTTP/cache refreshes. Rate edits reuse captured quotes and update the estimate without reconstructing the input field. Each side uses GEPL's last-hour average (`getOneHourAverage`; instant-buy for supplies and ingredients, instant-sell for outputs) when that side traded in the hour. Otherwise it falls back to the latest single trade, which is refused if it is more than 3x away from the other side's hourly average. One dumped or misclicked trade therefore can't swing an estimate. GEPL keeps its latest and hourly data separately and an item can appear in only one, so both are asked for and either is enough: an item with hourly trades but no latest entry is still priced, and hourly prices are used while the latest data is still loading. An hourly average carries no trade timestamp of its own; the traded volume shows the item is trading. Prices can be stale or illiquid; raw timestamps stay in calculator evidence rather than the player-facing table. An incomplete source model prevents a profit estimate. A missing price doesn't have to: when more of a side's market-priced rows (supplies, or outputs) have prices than don't, the missing ones count as 0 GP, so one thinly traded potion or rare drop doesn't hide the whole method. The status line and the Browse tooltip name them, and each row's hover says so. A missing output counted as 0 only understates the profit; a missing supply can overstate it a little, and its row's hover warns of that. Coins and other fixed values don't count towards the majority, and a side whose only row, or most of whose rows, have no price still has no total, so neither does the profit. Hovering an "Unavailable" value says why (GEPL still loading, no GE prices for the item, no recent instant-buy or instant-sell trades, a refused one-off trade, or the ingredient a creation cost is missing), and the status line names the first missing item. No snapshot-price fallback or direct price polling is used. GEPL 0.3.1's getLatest applies its own cache-expiry and in-flight guards, so rapid reopening does not force repeated HTTP refreshes; Profit Path never calls updateDatabase directly.

The window uses your own character's visible display name (`Player.GetEntity().displayName`) without tracking permission. Settings are local to this device. On first use, the current character keeps the previously selected profile's rates/favourites; later characters get separate bindings. Existing saved records and keys are preserved. Name reads and storage failures stop opening rather than writing under another character. Display-name changes are not a stable identity signal: old bindings remain stored and may need an explicit reassignment after a rename.

Method details place Back, title and favourite on one header row. Shaded input/output tables align hourly quantities and totals. The centered method title shares a row with Back and favourite. Hourly input/output totals share the section heading row; hover Inputs or Outputs for pricing assumptions. A single Rate per hour label accompanies the input, a floppy-disk save icon and an undo/reset icon. Notes describe pricing assumptions and gameplay caveats rather than refresh mechanics. A valid rate edit previews immediately. Press Enter or **Save** to persist it; **Reset to source rate** deletes that override. Invalid input keeps the last valid estimate. Save/reset failures remain visible, and changing units invalidates an old saved rate with a warning.

Save a custom rate, reload and confirm it remains under the same profile. Reset and confirm 2,000 returns. Check the after-tax labels, all four tabs, Back, resizing and repeat reload/close cycles. Automated tests do not establish native rendering or persistence behavior.

## Local reference data

The build includes a copied monster/drop snapshot and four representative method-version records. Method data now feeds the browser/calculator. PvM loot selectors now expand shared monster drops into expected outputs per kill. Exact rates and average quantity ranges are validated using the same Lua expansion at build time; ambiguous multi-rate entries require an explicit source-selected rate. The runtime caches static expanded definitions and rate edits reuse captured GE quotes. No recommendation engine uses it yet.

`catalogue-source/monsters.json` is the readable source, with original input hashes and provenance. `data/monsters.lua` is generated: repeated strings, drop rows and sections are stored once. `src/data/monster_data.lua` looks up exact Wiki titles and returns fresh plain tables, decoding only the requested record. No Monster Data Core or Monster Lookup dependency is required, and no network requests occur. The snapshot covers 1,120 monster pages from the inherited bundle built 2026-10-22; this is not full current Wiki coverage.

The import retains drop quantities, rates, rolls, ranges, modes, conditions and notes. It omits combat stats, maps, locations, search indexes and historical prices. Unknown rates/quantities remain unknown. The inherited snapshot does not provide individual article revisions. Notices are in `THIRD_PARTY_NOTICES.txt`; full inherited notices are retained with the source inputs.

`catalogue-source/methods.json` is a short hand-edited source (schema 2): one entry per Wiki page, whose `versions` list only what differs from the page. Requirements may be short strings (`skill:SMITHING:20`, `item:31455`); the build fills in requirement text, ANY/ALL group wording ("A or B", "A; B"), item-group icons, the " (recommended)" ending on recommended entries, income row names from the items table, Wiki links from page names and revisions, and empty lists. It then validates the full records and packs them into `data/methods.lua` (shared text and record shapes), which the plugin reads only through `src/data/method_data.lua`. Each full record carries `schema` 1 and `origin` "bundled", so later player copies can share the same shape. The source records the initial steel-bar, elder-log (without and with wood spirits) and abyssal-demon methods with Wiki revisions. Records sharing a title are versions of one method: Browse lists each version as its own "Title - Version" row, and the method page shows the title followed by a version dropdown that switches to another version (its own prices and saved rate) on the same tab. The build requires distinct version labels and one activity category per title. The wood-spirit version uses the source's 260 spirits per 580 logs, scaled with the logs-per-hour rate. Method quantities explicitly distinguish per-action and hourly costs. The PvM entry references selected shared drop rows instead of copying them. The PvM income model is now complete; account gear/quest readiness remains partial. Its 16 expected outputs match the pinned Wiki quantity expressions. Salvage uses actual spring-cleaner high-alchemy proceeds, with the existing spring supply cost, rather than the Wiki table's GE salvage prices. Coin drops and alchemy proceeds are untaxed; other outputs use GE sell prices after tax. Wand/orb rates assume a Slayer task; luck and Most Wanted-card bonuses are not included. The untradeable elder-log Perfect plus potion and abyssal-demon Aggroverload are priced by creation cost (below); Super prayer renewal is tradeable and uses its GE price. Item references are resolved to native Obj configs and checked against their expected names for icons; that visual check does not establish ownership or usability. Untradeable supply rows name a recipe (`"pricing": "recipe"`, a Wiki page and dose count); the build rejects unknown recipes, dose mismatches and recipe pricing on outputs.

**Creation costs.** Untradeable supplies (e.g. Perfect plus potion, Overload, Dungeoneering summoning pouches) have no GE price, so Profit Path prices them by what they cost to make: each ingredient at its GEPL instant-buy price (hourly average where available), following untradeable ingredients through their own recipes and scaling by doses (one Overload (4) is 4/3 of the 3-dose Overload recipe). The first (standard) Wiki recipe is used; perk-only batch recipes stay in the source but are not chosen. Ingredients with no price at all (e.g. Crystal tree blossom, charms) count as free, and the method's Notes name them. By-products such as returned vials are ignored. A missing GE price for any ingredient leaves the cost unavailable, naming that ingredient and why it has no price. The shown timestamp is the oldest ingredient price used. A Wiki guide row priced with `{{potioncost|potion}}` and no dose is one finished potion as the recipe makes it (a 6-dose elder overload), per the template's documentation, so it uses our recipe too. Rows priced with an improved recipe tier (`potioncost|adrenaline renewal 2`), and untradeables without a Herblore or Summoning recipe (Divination signs, XP capacitors, the potion reservoir, the overload flask), keep the Wiki's calculated value, labelled as such.
